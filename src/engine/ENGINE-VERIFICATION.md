#### 三层校验的精度（各不相同，**不得写成"系统容差 1e-6"**）

内容数据 2026-11-05 指出：我把引擎侧的精度边界说成"两边都不会报告"，把它泛化到了**数据侧**，**这是错的**。
三层比的东西不同，容差也就不同：

| 层 | 比什么 | 判据 | 边界 |
|---|---|---|---|
| **引擎** `match()` | 六维权重的**和** 与 1.0 | `\|sum-1\| > 1e-6` 则告警 | 单维偏 **1e-7 不告警**（浮点累加必然有误差，必须留容差） |
| **API** `checkTheme()` | 同上 | `\|sum-1\| > 1e-6` 则拒绝下发 | 同上 |
| **数据** `validate-data.mjs` | 数据值 与 引擎常量**逐项字面量** | `data[k] !== engine[k]`，**无容差** | **`0.1800001` 立刻 FAIL** |

**为什么数据侧不用容差**：它比的是两个 JSON 字面量（`0.18` 与 `0.18`），**中间没有运算，精确相等成立**。
给它加 `1e-6` 反而是错的——那会放过 `0.1800001` 这种**真实错位**，而这正是引擎层"必须容忍"、数据层"绝不该容忍"的那一类。

**所以「1e-7 量级的错位测不到」这条边界只存在于引擎层与 API 层，数据侧不存在。**
实测脚本：`example/check-theme-tolerance.ts`（引擎侧边界）。

> **补一格：API 层抓不到「逐项错位但和不变」**（后端开发 2026-11-05 实测）
>
> 注入 `EE=0.1800001 / SR=0.1199999`：**权重和仍是精确的 1.0**，`checkTheme()` 必然放行；
> 数据侧逐项字面量比对则立刻 FAIL。
>
> 这不是缺陷，是分工：**API 守「整体比例对不对」，数据侧守「每个数抄没抄对」**。
> 三层精度**不可互推**，所以本文档禁止写成「系统容差 `1e-6`」。
>
> ⚠️ **读本表的人最容易踩的坑**（内容数据 2026-11-05 补充）：看到「权重和 = 1.0 通过」，
> **不要以为这类问题已经被排除**。和 = 1.0 **只说明比例没被整体改变**，**对「每个数有没有抄对」不提供任何保证**——
> `EE=0.1800001 / SR=0.1199999` 就是和精确为 1.0 的反例。
> **两条结论必须分别说：「比例正确」和「逐项正确」；前者推不出后者。**

> **再补一格：`1e-6` 为什么是这个值**（后端开发 2026-11-05 提出「1e-6 是凭直觉选的、说不出理由」，此格补上理由）
>
> **下界由浮点误差定**：六个数相加的累加误差上界为 `n·u·Σ|x|`，其中 `n=6`、`u=2^-53≈1.11e-16`、`Σ|x|=1`，
> 得 **≈6.7e-16**。容差必须显著大于这个数，否则正常数据会误报。
>
> **上界由数据精度定**：权重写成两位或三位小数（`0.18` / `0.183`），任何真实错位至少是 `1e-3` 量级。
> 容差必须显著小于这个数，否则真错会被放过。
>
> **`1e-6` 落在这个窗口内偏下界一侧**，相对 6.7e-16 余约 **1.5e9 倍**，相对 1e-3 的真错留约 1e3 倍判别力。
> **选 `1e-9` 也不会错**（余量 1.5e6 倍，仍够宽），只是对真错的判别余量小一些——所以 `1e-6` 是
> **窗口内的合理选点，不是唯一解**；能说清的是「下界是多少、上界由什么决定」，而不是「必须恰好 1e-6」。
>
> ⚠️ 本节只解释**引擎/API 层**的容差取值。**数据层仍是无容差的严格相等**，见上表——不要因为本节写了 `1e-6` 就在数据侧也用。
