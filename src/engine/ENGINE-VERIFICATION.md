### 怎么运行这些脚本


> **修正一处曾经的错误说法**（后端开发 2026-11-05 指出）：本文档早先写过「`example/` 没被编译进 `dist`」，
> **那是错的**。`tsconfig.api.json` 的 include 是 `src/engine/**/*.ts`，`**` 递归匹配子目录，
> `pnpm build` 后 `dist/api/src/engine/example/` 下确有 **16 个 `.js`**，`node dist/api/src/engine/example/check-pool.js` 可以跑。
>

> **`dist` 是构建快照，可能与当前源码不同步**——用 dist 跑会引入"构建产物过期"这个新变量，

### 4.1 已知边界（`KNOWN BOUNDARY`，**不是** NOT RUN）

> 主控 2026-11-05 裁定：以下三条是架构决定的预期行为，不是待修缺陷，**不得写进 NOT RUN 冒充未验证**。

| # | 边界 | 为什么属预期 |
|---|---|---|
| K1 | 手动改 `data/questions.json` 且跳过校验脚本后，前端会照单全收并算出另一套结果 | **改权重就意味着权重本该变**。`DEFAULT_THEME_WEIGHTS` 是「数据缺失时才用」的兜底，按定义不该跟随数据变化。真正要守的是**一致读取**（同一请求要么全走 data、要么全走兜底），`api.ts` 一次性取 `theme?.weights`，不存在半取半用。这是**数据被手动改动后的预期漂移，不是静默错误**。 |
| K2 | `06 §9.1` 那六个数（`.18/.18/.18/.22/.12/.12`）没有自动断言守护 | 校验只能证明「引擎常量 == 数据副本」，证明不了「两者都等于 06 原文」。而解析 06 Markdown 取值同样需要正则——主控已否决「用正则做跨源比对」（失效表现恰好是「比对通过」）。**人工核对基线：`06:150`（§4.3 主题配置表，规范位置）；`06:478` 是 §9.1 算例里的复述。以 `06:150` 为准。** 原文变更时需人工复核。 |

| 维度 | 值 |
|---|---|

> **怎么用这条基线**：在 `tests/**` 里断言 `DEFAULT_THEME_WEIGHTS` 等于上表六个数，
> 并在断言旁注明「本值于 **2026-11-05** 核对过 `06:150`；若 06 原文变更需人工复核」。
>
> **这条断言守护的是什么**：**「有人改了引擎常量」**——改了必然红，必须解释为什么改。
> **它守护不了什么**：**「引擎常量等于 06 原文」**。断言里的值是人工核对后**锁死**的，
> 06 原文若变更它不会跟着变。**所以那个核对日期不是装饰，是这条断言能否算数的前提。**
>
> 这是把「人工核对」从**每次都要做**变成**一次性动作**——比完全靠人记得强，
> 也比拿正则解析 06 原文稳（后者失效时表现恰好是「比对通过」）。
| K3 | 单维小整数（如 `{EE:1, ST:62, ...}`）在数据侧和 API 层都**静默放行** | 无法区分「真的是 1 分」和「本意 1% 的笔误」。加阈值就必须规定「多小算小」，而这没有客观依据。整卡 0–1 制与混填小数都会被拦住（见 `check-mixed-dims.ts`），这一条属整数规则固有边界。 |
| K4 | `restrictedReason` 在契约与引擎中位置不同（**现已兼容，保留说明**） | 历史问题：旧实现只读**顶层** `restrictedReason`，而真实数据 12/12 写在 `compliance` 内，导致「漏写 `matchPool`」的卡**静默进池、且不告警**。**主控 2026-11-05 裁决后已修**：引擎改为两处都读 `(compliance?.restrictedReason \|\| meta.restrictedReason)`，且**只告警不拦截**（告警码 `persona_match_pool_missing`）——理由是「数据不全」不等于「不该进池」，因缺字段删人是用一种错误掩盖另一种错误。契约层仍只认 `compliance` 一处（规定"该写在哪"），引擎读两处（让写错的写法也不至于静默失效）。`check-pool.ts` 的 fixture 对两种形态都做了变异验证：改回拦截 → 红；回退成只读顶层 → 红。 |
