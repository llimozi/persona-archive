## 3. 已发现并修复的缺陷（记录在案）

### BUG-1 「重测」按钮宽度异常（视觉缺陷，已修）

- **现象**：修复前实测 `重测` 为 **251×44**（390px）/ **224×44**（360px），一条顶栏动作按钮被拉成半屏宽。
- **根因**：CSS 层叠问题。`.btn` 上有 `width: 100%`，`.btn--quiet` 只覆盖了颜色与字号，没覆盖宽度，于是继承了满宽。
- **影响性质**：**视觉缺陷，不是可用性缺陷**。修复前高度已是 44px，热区达标；问题在视觉比例失真。两者性质不同，不可混为一谈。
- **修复**：`src/web/styles/app.css` 的 `.btn--quiet` 补 `width: auto; padding: 0 var(--sp-3)`。
- **复测**：52×44（两个视口一致），高度仍 ≥44 ✅。

### BUG-2 答题进度刷新即丢（功能缺陷，已修）

- **现象**：答到第 4 题刷新页面，回到首页，10 题答案全部丢失。微信里切后台被回收时同样丢失。
- **根因**：两层。① 答题状态只存在 React 内存里，没有持久化；② 第一版用 `useEffect` 恢复时，与"保存 effect"发生竞态——首帧先用空初始值写了存储，把存档覆盖掉。
- **修复**：`src/web/App.tsx` 改用惰性初始化（`useState(() => loadProgress())`），首帧直接读存档；`sessionStorage` key `pa.quiz.v1`，存 `{index, answers, screen}`；点「重测」清空。
- **复测（VERIFIED）**：
  - 答到 `4 / 10` 刷新 → 仍在答题页、题号 `4 / 10`、题干为第 4 题，**不回首页** ✅
  - 当前题已作答时刷新 → 已选选项正确回填（`aria-pressed="true"` 计数 = 1）✅
  - 存储内容前后一致：`{"index":3,"answers":{...4 题},"screen":"quiz"}` ✅

### BUG-3 题库到达前后题号可能越界（防御性修复）

- **场景**：存档题号来自旧题库，题库变短后 `questions[index]` 取空，`QuizPage` 返回 `null` 出现白屏。
- **修复**：题库加载完成后把 `index` 夹到 `[0, len-1]`。
- **复测**：10 题下无越界，正常。**状态：VERIFIED（当前数据下无异常，防御分支未单独构造样本验证）**

## 5. 断言缺陷（不是产品缺陷）

**这一类我犯过两次，都是「测法错」而不是「产品错」，记录在此，避免下次再犯。**

### A-1 把「按钮 disabled 未提交」误判成「选项点不动」

- **现象**：自测脚本在同一个 JS evaluate 里「点选项 → 立刻点下一题」，按钮 `disabled` 还没被 React 提交更新，点击被吞，流程停在第 1 题，最终断言「结果页主人物为空」。当时我把这个现象描述成「答题页选项按钮点不动」，**并让主控以为这是产品 bug**。
- **正确判定依据**：改用 CDP `Input.dispatchMouseEvent` 发真实鼠标事件，并在两次点击之间等待 React 提交后，10 题逐题全部可点（每次点击后 `aria-pressed=true` 计数 = 1、`下一题.disabled = false`），结果页正确渲染「奶龙」。
- **结论**：**断言缺陷，非产品缺陷**。产品侧选项与按钮本身完全可点。
- **修正**：`scripts/viewport-audit.mjs` 拆成「点选项 → sleep → 点下一题」两步。

### A-2 把「当前题本来就没答」误判成「答案没回填」

- **现象**：验证进度恢复时，我刷新后检查 `aria-pressed="true"` 计数，得到 `pressed: 0`，据此一度以为「已选答案没回填」。
- **正确判定依据**：当时停在的是第 4 题，而第 4 题**本来就没有作答**（前 3 题答完即前进），所以 0 是正确值。补做「先答当前题再刷新」的用例后，`pressed: 1`，答案回填正常。
- **结论**：**断言缺陷，非产品缺陷**。断言没有区分「当前题是否已作答」。
- **教训**：断言要针对被测对象的真实状态写，不能拿一个恒为真的现象当证据。

## 5.2 联调期 502 的定性（测试环境特性，非产品已知限制）

**现象**：联调期间 `/api/personas` 偶发返回 `502`（后端改造后带 `upstream_unavailable` 与上游地址）。

**定位证据**（三条同时成立）：
- 直连 `127.0.0.1:8787/api/health` → 200
- 走 Vite 代理 `5173/api/personas` → 502
- 再走一次 → 200

**成因**：`tsx watch` 因文件改动重启，重启窗口内上游不可达，Vite 代理拿不到后端。

**定性**：**这是测试环境特性，不是产品已知限制。** 生产环境跑的是不带 watch 的构建产物，不存在这个窗口。不得把它登记为「产品缺陷」或「已知边界」。

**对测试的要求**：E2E 必须跑在**不带 watch 的稳定实例**上（构建产物或非 watch 模式），固定 PID 再跑；不能因为"知道它会 502"就接受偶发失败。


原先 `?r=` 无人认领（原分工表里的「竞品研究」角色不存在），因落在 `src/web/**` 由前端补齐。

**实现**：`src/web/lib/share.ts`，把作答序列自包含编码进 URL（`?r=<base64url(JSON)>`），**只编码 answers，不编码人物结论** —— 结论由引擎按当前数据重新算，避免「链接里的结论」与「当前引擎/数据」不一致。UTF-8 安全编码，规避微信内置浏览器 `btoa` 非 ASCII 差异。

**实测（VERIFIED）**：

| 用例 | 结果 |
|---|---|
| 结果页生成 token | 242 字符 |
| 清空本地存档后以新会话打开分享链接 | 直接进入结果页 ✅ |
| 他人打开后的主人物 | 奶龙（与原结果一致）✅ |
| 他人打开后六维行数 | 6 行完整 ✅ |
| 坏 token（`?r=!!!bad-token###`） | 静默降级回首页，无报错弹层 ✅ |
| 点「重测」 | 清空 URL 里的 `?r=`，不会分享出旧结果 ✅ |

**未验证**：微信内实际分享卡片呈现、`navigator.share` 在真机上的行为，均为 **NOT RUN**。

### 分享链接的语义（产品承诺，必须如实对外）

> **`?r=` 链接的语义是「用当前数据重放这份作答」，不是「锁定当时的结论」。**

链接里编码的是**原始作答**（`encodeAnswers`），不是结果快照。因此：

- 同一个 `?r=` 链接，今天打开是 A 人物，若明天有人改了某题的 `effects` 或某人的 `dims`，再打开可能得出另一个结果
- **这不属于缺陷**，是「重放」方案的固有取舍

**为什么不用快照**：存结果快照需要后端存储，而技术栈已定「不做数据库、不做 ORM」；且旧结论配上新数据的解释文字会自相矛盾。重放是正确取舍，但必须如实告知。

**对外文案红线**：
- 不得写「永久有效」
- 不得写「别人看到的和你完全一样」
- 可写「打开链接的人会看到同一份作答算出的结果」

### 权重来源

主题权重优先读 `/api/questions` 下发的 `theme.weights`（`data/questions.json` 为权威源），缺失时回退引擎 `DEFAULT_THEME_WEIGHTS`（06 §9.1 设计值，非实测）。

**切换后复验**：从引擎兜底切换到数据源后，全选 A 的六维输出**逐位不变**（100/81/100/100/73/21，逐维差全为 0）。这说明切换没有引入数值变化，符合内容数据"两边同值"的比对结论。
